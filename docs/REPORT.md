# FieldMate: technical report

*Small language models for offline drone field operations on a 2-vCPU ARM64 CPU box.*
Rakesh Burla, November 2026. All numbers come from `results/` and were produced by the harness in
`src/fieldmate/bench/`; the tables in section 3 are generated by `scripts/make_tables.py`.

## 1. Problem and summary

Drone crews need their field notes turned into records a maintenance system can trust (pre-flight
go/no-go checks, defect reports) and need answers about their fleet log, often with no internet
and with data that should not leave the site. FieldMate does this with 1B to 4B parameter models
served by Ollama on CPU, using JSON-schema constrained decoding, Pydantic v2 validation with
ops-manual rules, and one retry with error feedback.

**Findings in one paragraph.** All four models reached 100% schema-valid output after at most one
retry. Accuracy, not validity, separates them: `qwen2.5:3b` extracted 85.8% of fields correctly
(95% go/no-go) at 12.6 decode tok/s and 2.3 GiB RAM, against 61.8% for `llama3.2:1b`, which is
1.8x faster (22.5 tok/s, 1.7 GiB) but gets one go/no-go call in five wrong. `phi4-mini` and
`llama3.2:3b` were perfect on fleet-log Q&A but slower or weaker on ids. Removing the grammar
constraint cut validity to 69.4% and doubled latency. Q4_K_M quantization of the 1B model saved 31%
RAM for a 1.7-point accuracy loss on extraction, but cost more on free-text Q&A. Recommendation:
`qwen2.5:3b` (Q4_K_M) as the default.

## 2. Setup and method

### Hardware (the "edge box")

| Item | Value |
|---|---|
| CPU | 2 vCPU, ARM64 (aarch64), NEON + dotprod; llama.cpp picks the `armv8.x` CPU backend |
| RAM | 7.8 GiB total, **no swap** |
| GPU | none |
| OS / runtime | Linux container, Python 3.12, Ollama 0.40.15 (llama.cpp `llama-server` runner) |
| Model storage | network filesystem (JuiceFS/FUSE), which makes cold loads slow |

This is roughly the class of machine a drone team would actually carry: a small ARM board or
an old laptop, CPU only. Important caveat: the box was **shared with other heavy workloads**
during the runs (1-minute load average 3 to 9 on 2 cores, and between 0.1 and 2.9 GiB of free
RAM). Every result file records the load average and free RAM at the start of the run, and the
memory gate in `scripts/wait_for_memory.py` only starts a model when there is room for it.
Absolute speeds are therefore pessimistic. The comparisons between models were run back to back
under the same conditions, so the ranking is more trustworthy than any single number.

### Ollama configuration

* Defaults: weights loaded into RAM (Ollama disables mmap on CPU), llama.cpp ARM weight
  repacking on, 1 parallel slot, 1 loaded model.
* `num_ctx = 2048` (all prompts fit; a smaller KV cache saves RAM on a 7.8 GiB box).
* `LLAMA_ARG_CACHE_RAM=0`: llama-server's host-RAM prompt cache (default 8 GiB) is disabled so
  RAM use stays flat. In-slot prefix reuse still works, so the fixed system prompt is processed
  once and only the new note is pre-filled. That is what a real deployment would see.

### What is measured, and how

| Metric | Definition | Source |
|---|---|---|
| Decode tokens/s | `eval_count / eval_duration` | Ollama response timings |
| Prefill tokens/s | `prompt_eval_count / prompt_eval_duration` | Ollama response timings |
| TTFT | request start to first streamed content chunk | client clock (`time.perf_counter`) |
| Latency | request start to final chunk, all retries included | client clock |
| Cold load | `load_duration` of the first call after `keep_alive=0` eviction | Ollama |
| Peak RSS | max over 250 ms samples of RSS(ollama serve + llama-server) | `psutil` thread |
| Schema-valid | output parses as JSON and passes Pydantic v2, ops rules included | `extractor.py` |
| Field accuracy | share of scored fields equal to the hand-labelled answer | `bench/scoring.py` |
| Q&A rubric | share of required facts (any listed synonym) present in the answer | `bench/scoring.py` |

Statistics are reported as mean, p50 and p95 (linear interpolation). Each warm perf run uses a
*different* question or note, so the prompt cache only helps with the shared system prompt.

### Test set (`data/testset.jsonl`, 42 items, hand-labelled)

* 20 **pre-flight notes** -> `PreflightReport`. Eight fields are scored: aircraft id, battery %,
  propellers / motors / GPS / compass status, weather ok, go/no-go.
* 16 **defect notes** -> `DefectReport`. Four fields are scored: aircraft id, component,
  severity, grounded.
* 6 **fleet-log questions** answered from a 6-line maintenance log and graded by keyword rubric.

The notes are written the way pilots actually write: lower-case ids, "batt 88", "didnt check
compass", unit-less numbers, and distractors such as "compass warning ... moved 10 m and it
cleared -> ok". A unit test checks that every expected answer itself passes the schema and the
ops rules, so the labels and the validator cannot disagree.

## 4. Analysis

**Speed is set by parameter count and memory bandwidth.** Decode speed fell from 22.5 tok/s (1.2B,
Q8_0) to 12.6 (3.1B qwen), 10.4 (3.2B llama) and 9.0 (3.8B phi4-mini, all Q4_K_M), roughly in line
with bytes of weights read per token. Time to first token is dominated by prefill of the ~450-token
extraction prompt: 3.1 s on 1B vs 9.8 to 13.1 s on the 3-4B models (prefill 32-42 tok/s). For a
crew batch-processing notes at the end of the day, about 7 s per note (`qwen2.5:3b` p50 in the
quality run) is acceptable; for interactive use, streaming hides most of it.

**Validity is solved by the stack, accuracy is not.** With the schema as a grammar and one retry,
144 of 144 extractions were valid. The retry mattered most for `llama3.2:3b` (13.9% of
extractions needed it). What still goes wrong is content: severity grading on defect notes (18.8%
for 1B, 62.5-68.8% for the others), aircraft ids on defect notes for `llama3.2:3b` and `phi4-mini`
(62.5%), and the nullable fields.

**The null escape hatch.** `battery_pct` and `weather_ok` may be `null` when a note does not state
them. Under constrained decoding the models often chose `null` even when the note said "batt 88":
`llama3.2:1b` did so on 20/20 pre-flight notes, `phi4-mini` on 18/20, `llama3.2:3b` 14/20, and
`qwen2.5:3b` 9/20. The ablation shows this is linked to the grammar: without it, the 1B model read
the battery correctly on 15 of 15 valid pre-flight outputs. Battery below 30% must force a no-go,
so this matters for safety: in production I would make the field required with an explicit
"not_stated" sentinel, or extract numbers with a regex pre-pass and let the model only classify.

**Constrained decoding is still the right default.** Without the grammar, only 47.2% of 1B outputs
were valid on the first try and 69.4% after the retry; failures were invalid enum values
(`component`, 12 errors), `issues` returned as a string (10) and ops-rule violations (4). The
retries doubled p50 latency (7.8 s vs 3.7 s per item). A tool that silently drops 31% of notes is
worse than one that is sometimes conservative.

**Temperature.** At T=0, 31 of 32 runs matched the most common output; at T=0.7 only 42% of
extraction runs and 62.5% of Q&A runs did, with a 0.15 standard deviation in field accuracy per
note. T=0 mistakes are repeatable (two notes failed on all four runs), which is why the retry with
error feedback, not sampling, is the recovery mechanism.

**Quantization.** For `llama3.2:1b`, Q4_K_M kept extraction accuracy within 1.7 points of Q8_0
(60.1% vs 61.8%) and Q5_K_M matched it exactly, while peak RSS fell from 1.72 to 1.19 GiB (-31%).
Free-text Q&A degraded much more (rubric 58.3% to 25.0%), on only 6 questions. Re-running Q8_0
reproduced all 36 extraction outputs of the main study, so the accuracy comparison is not noise
from non-determinism. Speed comparisons between the three builds are confounded by host load
(1-minute load 2.1, 4.4 and 5.9 during the three runs); the cleanest pair is Q4_K_M at 30.1 tok/s
(load 2.1) vs Q8_0 at 22.5 tok/s (load 0.3), at least 34% faster.

**Recommendation.** `qwen2.5:3b` (Q4_K_M) is FieldMate's default: best accuracy, 95% go/no-go,
2.3 GiB, mid-pack speed. Use `phi4-mini` where Q&A quality matters more than latency, and
`llama3.2:1b` Q4_K_M only on boards with under 2 GiB free and with human review of decisions.
`mistral:7b` was excluded: 4.1 GB of weights plus KV cache did not fit beside the other workloads
on the 7.8 GiB, swap-less host.

## 5. What went wrong, and the fixes

1. **The runner was OOM-killed on a shared 7.8 GiB box.** Ollama on CPU turns mmap *off* and
   copies the weights into process memory, and llama.cpp's ARM weight repacking makes another
   resident copy. `llama3.2:1b` (Q8_0, 1.3 GB on disk) reached 1.7 GB anonymous RSS, and the
   kernel log shows `Out of memory: Killed process ... (llama-server)`. Other jobs on the box held
   up to 5 GiB of RAM-backed `/tmp`, so free memory moved between 0.1 and 2.9 GiB from minute to
   minute. *Fixes:* (a) `scripts/wait_for_memory.py` only loads a model after three readings in a
   row, 10 s apart, show enough free RAM for it (one good reading was not enough: a load passed
   the gate at 2.9 GiB and was still killed); (b) a circuit breaker stops a model's run after two
   Ollama errors in a row instead of writing 42 rows of failures; (c) every result row is
   appended to JSONL as soon as it exists, so a run that gets killed resumes where it stopped;
   (d) `LLAMA_ARG_CACHE_RAM=0` turns off llama-server's 8 GiB host prompt cache.
2. **mmap is not a free lunch.** I tried `use_mmap=true` with repacking off, so the weights live
   in reclaimable page cache. Under memory pressure the kernel kept evicting them and re-reading
   them over the network filesystem: about 1 token/s, and a 284-token prompt took minutes to
   pre-fill. The mode stays available as `FIELDMATE_USE_MMAP=1` for hosts that have the RAM, but
   it is off by default. Lesson: on an edge box, budget RAM for the whole model plus about
   0.5 GiB. Do not count on paging.
3. **The 1B model copied the example from the prompt.** The first system prompt said
   "Aircraft IDs are upper-case like UAV-07". `llama3.2:1b` then labelled a Q4-ALPHA note as
   UAV-07. I changed the example to `XY-12`, and the model wrote `XY-12` for every defect.
   *Fix:* no example values in prompts for tiny models. The instruction now says "copy the
   aircraft ID from the note". Both prompt versions are in git history.
4. **Local traffic went through a proxy.** The sandbox sets `HTTP(S)_PROXY`, and httpx honours it
   by default, so requests to `127.0.0.1:11434` came back empty. *Fix:* the client uses
   `trust_env=False`. An offline tool should never send local inference traffic through a proxy.
5. **Identical prompts made TTFT look too good.** In early runs every warm request reused the
   first one's KV cache (prefill showed about 1,000 tok/s). *Fix:* each warm run now uses a
   different question or note, so only the shared system prompt is cached, as in real use.
6. **`pgrep -f` killed my own shell.** Housekeeping scripts that matched on the command line
   also matched the shell running them. `scripts/` now matches on exact process names. A small
   thing, but it cost several reruns.
7. **The RAM gate waited for memory the previous model was holding.** With `keep_alive=30m`,
   `phi4-mini`'s runner (3.3 GB resident) stayed loaded after its quality run, so the gate for
   the next model (needs 2.7 GiB free) saw about 2.7 GiB and kept waiting, while the box sat
   idle. *Fix:* `scripts/wait_for_memory.py` now asks Ollama to unload any resident model
   (`keep_alive: 0`) before it starts counting free RAM.
8. **Nullable fields became an escape hatch.** The schema allows `battery_pct` and
   `weather_ok` to be `null` ("not stated"). Under grammar-constrained decoding the models,
   above all the 1B one, often chose `null` even when the note said "batt 88": `llama3.2:1b`
   returned `null` battery on 20 of 20 pre-flight notes. This was found by the per-field table,
   not by the headline validity number (100% valid after retry). It is reported as measured, not
   fixed after the fact; see future work.

## 6. Limitations

* 42 hand-labelled items (6 Q&A) written by one person; differences of a few points are within
  noise, and Q&A differences are one or two questions. No confidence intervals are reported.
* The host was shared: 1-minute load averages of 0.3 to 5.9 on 2 cores during runs, so absolute
  speeds are pessimistic and the quantization speed comparison is confounded. Every result row
  records the load average.
* One hardware platform (ARM64 CPU, no GPU), Ollama 0.40.15, default library quantizations.
* The temperature study covers one model, 8 prompts and 4 runs per temperature.
* Field accuracy is exact match per field; partially right free text (`issues`) is not scored.
* The sandbox rebooted once mid-run; resumable JSONL meant no finished phase was lost. Partial
  quantization rows from two interrupted attempts (9 and 7 rows, recorded under much heavier load)
  were discarded and the quantization phase was re-run from scratch for consistent latencies.
